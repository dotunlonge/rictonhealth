# Ricton Web Frontend — Design and Product Audit

**Audited:** 2026-09-04  
**Scope:** every route and shared visual file under `apps/web/src`, compared with all 106 source PDFs and seven JPGs in `RICTON_UI_UX/Web`  
**Purpose:** establish the professional visual direction that the React Native app should share

## Executive verdict

The implemented web frontend is a substantial visual improvement over the source boards. The source boards use a bright blue navigation rail, pale lavender/hex-pattern backgrounds, low-contrast text, long form canvases, and large areas of unstructured whitespace. The current site replaces that with a calmer navy shell, blue calls to action, slate neutrals, white surfaces, restrained gradients, modern icons, and stronger card hierarchy.

That improvement is real but uneven. The current site is a collection of well-styled pages rather than a governed design system. It contains hard-coded colors, tiny text, duplicated patterns, missing responsive navigation, placeholder interactions, contract drift, and role/access inconsistencies. Mobile should inherit the direction and rebuild it as semantic tokens and reusable primitives; it should not copy page-local Tailwind combinations.

## Design choices worth retaining

- Deep navy navigation/shell creates a credible clinical and enterprise tone.
- Bright blue is used most effectively as the single primary-action color.
- White/slate cards and subtle borders create better hierarchy than the source's decorative backgrounds.
- Restrained sky/blue gradients work for hero or premium emphasis when used sparingly.
- Lucide line icons feel more consistent than mixed custom icon treatments.
- Rounded cards, concise statistic blocks, and sectioned dashboards scan well.
- Geist gives the web product a clean, contemporary base; mobile should use a metrically compatible family with native text scaling.

## Design choices to correct before calling the system professional

### System-level

- Define semantic color, typography, spacing, radius, elevation, and motion tokens in a shared package. Do not expose literal web-only classes to mobile.
- Replace ad hoc page headers, cards, filters, tables, dialogs, form fields, badges, empty states, and alerts with governed components.
- Establish readable type floors. Nine- and ten-pixel UI labels are inappropriate for routine clinical use.
- Add responsive navigation. The current fixed 256 px sidebar is a desktop assumption, not a complete responsive shell.
- Treat focus, keyboard operation, screen-reader names, visible error text, and reduced motion as component requirements.
- Replace silent fallback-to-zero behavior with distinct loading, empty, stale, partial, and error states.
- Validate every marketing/compliance claim before it is reused on mobile or in stores.

### Product-level

- Remove dead links or ship their destinations.
- Make global search functional or remove it.
- Enforce roles at route and server boundaries, not only through hidden navigation.
- Replace raw API strings with generated client methods from the authoritative contract.
- Do not let patient/consultant pages call administrator-only analytics endpoints.
- Use backend status enums and response envelopes verbatim; do not invent client-only states.

## Web actions that precede mobile feature work

1. Fix the existing web TypeScript failures in settings and establish a clean baseline.
2. Resolve route/method/envelope drift through an authoritative OpenAPI contract and generated client.
3. Add semantic design tokens and migrate the shared web shell/components first, proving the token names in production UI.
4. Repair responsive navigation, type floors, focus/keyboard behavior, error states, and route guards.
5. Remove or implement dead actions/routes and review public claims.
6. Use the same token and API packages from the React Native foundation.

This sequence preserves the web's stronger visual decisions while preventing its current inconsistencies from becoming mobile architecture.
